Cẩm Nang Khái Niệm Kiểm Thử Phần Mềm
Dành Riêng Cho Lập Trình Viên (Developer)

Bạn là Dev được giao nhiệm vụ xây dựng hệ thống Quản Lý Test Case (TCM) nhưng đang bị rối bời giữa Test Case, Test Suite, Test Plan, Test Run, Test Execution, TestCaseVersion, Flaky Test, RTM...? Tài liệu này giải thích toàn bộ hệ thống khái niệm QA thông qua tư duy lập trình viên: từ mô hình OOP (Class vs Object), Git commit (Snapshot/Immutability), cho đến thiết kế bảng cơ sở dữ liệu (EF Core / Relational DB).

1 Tư Duy Cốt Lõi: Dev Nhìn Kiểm Thử Như Thế Nào?

OOP & Database Mindset

Lý do lập trình viên cảm thấy các thuật ngữ kiểm thử khó hiểu là vì QA dùng nhiều từ ngữ nghe tương tự nhau (Test Case, Test Plan, Test Run, Test Scenario, Test Suite...). Nhưng khi quy về Lập trình Hướng đối tượng (OOP) và Cơ sở dữ liệu Quan hệ (RDBMS), mọi thứ trở nên cực kỳ trong sáng và mạch lạc:

Thuật ngữ QA Tương đương trong OOP / Dev Ẩn dụ Đời thường (Bếp ăn) Đặc tính Cơ sở dữ liệu
Test Suite / Module Namespace / Folder / Package Cuốn sổ phân loại món (Khai vị, Món chính) Bảng TestSuites (Cấu trúc cây tự trỏ đệ quy ParentId)
Test Case (TC) Class / Blueprint / Interface Công thức nấu một món ăn cụ thể Bảng TestCases (Master data thư viện, không lưu kết quả Pass/Fail)
Test Step Method / Code Lines / Instructions Các bước cụ thể: Rửa rau -> Đảo chảo -> Nêm nếm Bảng TestSteps (Quan hệ 1-N với Test Case, có số thứ tự StepOrder)
TestCaseVersion Git Commit Hash / Immutable Snapshot Bản in công thức tại ngày ký hợp đồng tiệc Bảng TestCaseVersions (Read-only, bảo toàn lịch sử không bị sửa)
Test Plan Release Backlog Scope / Contract Scope Thực đơn tiệc cưới ngày 20/10 (Gồm những món nào) Bảng TestPlans (Chứa mục tiêu, phạm vi Milestone/Sprint)
Test Run CI/CD Pipeline Run / Job Process Ca trực bếp trưa ngày 20/10 bắt đầu nấu tiệc Bảng TestRuns (Một đợt chạy cụ thể trên môi trường Staging/Prod)
Test Run Item Job Task / Instance / Work Item Đĩa món X được giao cho đầu bếp Nam nấu Bảng TestRunItems (Ánh xạ Test Case vào Test Run, gán cho Tester)
Test Execution Execution Log / Attempt / Run Result Biên bản nếm thử của quản lý (Ngon/Mặn/Hỏng) Bảng TestExecutions (1 Item có N lần nếm; Pass, Fail, Blocked, ảnh lỗi)
3 Sai Lầm Chí Mạng Khi Dev Bắt Tay Thiết Kế Hệ Thống Quản Lý Test Case
  1. Sai lầm 1: Đặt cột Status (Pass/Fail) vào thẳng bảng TestCases.
    Hậu quả: Bảng TestCases là thư viện tri thức lâu dài (Master Library). Nếu lưu Pass/Fail ở đây, khi chạy đợt test mới (Sprint 2), kết quả của Sprint 1 sẽ bị ghi đè hoàn toàn, hệ thống mất sạch lịch sử báo cáo!
  2. Sai lầm 2: Ghi đè (UPDATE) dòng kết quả khi tester thực thi lại (Re-test).
    Hậu quả: Khi test lần 1 bị Fail, Dev fix bug xong Tester test lần 2 ra Pass. Nếu UPDATE đè, bạn sẽ không thể thống kê được: "Bao nhiêu % test case phải chạy từ 2 lần trở lên mới Pass?" (Chỉ số Defect Reopen Rate / First-Time Pass Rate).
  3. Sai lầm 3: Không tạo Snapshot (TestCaseVersion) khi gán kịch bản vào đợt test.
    Hậu quả: Sang tháng sau, một bạn tester khác vào sửa nội dung bước 3 của Test Case. Báo cáo nghiệm thu của tháng trước bị thay đổi nội dung ngầm mà không ai hay biết!

2 Sơ Đồ Phân Cấp & Dòng Chảy Thực Thi Trong TCM

Life-cycle & Execution Flow

Trong hệ thống TCM chuyên nghiệp (như TestRail, Zephyr, Xray), toàn bộ dữ liệu luôn được chia làm 2 Thế Giới Riêng Biệt: Kho Thư Viện (Design Time - Repository) và Đợt Chạy Kiểm Thử (Execution Time - Run Cycle).

Dòng Chảy Vận Hành Từ Kịch Bản Đến Báo Cáo Xuất Xưởng 1-N & Snapshot Relationship
01. Tổ chức
Test Suite
Folder / Module

Cây thư mục phân loại: Authentication, Cart, Checkout, Admin...

02. Thiết kế
Test Case
Template / Steps

Kịch bản chi tiết: Tiền điều kiện, từng bước thực hiện, kết quả mong đợi.

03. Đóng băng
TC Version
Immutable Snapshot

Chốt phiên bản v1, v2 khi đưa vào chạy để không bị sửa đổi ngoài ý muốn.

04. Kế hoạch
Test Plan
Sprint Scope

Gom phạm vi kịch bản cho Sprint 24, Release v2.1, Milestone Q3.

05. Đợt chạy
Test Run
Execution Session

Đợt chạy trên môi trường thực tế (Staging, Android, iOS, Chrome v124).

06. Ghi nhận
Execution
Attempts (1-N)

Lần 1: Fail (kèm ảnh lỗi, link Jira) -> Dev fix -> Lần 2: Pass!

Thực thể Tần suất tồn tại Ai thao tác chính? Hành động khi có tính năng mới
Kho Kịch Bản (Test Cases) Vĩnh cửu theo vòng đời dự án (Tăng dần theo thời gian) QA Lead / Senior Tester Viết thêm kịch bản mới hoặc cập nhật version kịch bản cũ
Kế hoạch (Test Plan) Theo từng Sprint / Milestone / Phiên bản Release QA Lead / Project Manager Tạo mới cho mỗi Sprint, chọn các Test Case cần chạy
Đợt chạy (Test Run) Tạo liên tục theo mỗi bản build / môi trường kiểm thử Tester / CI Pipeline Automation Kích hoạt chạy trên Staging, Mobile, hoặc chạy tự động
Lịch sử chạy (Test Execution) Bất biến (Insert-only, không bao giờ UPDATE đè) Tester / Test Runner Agent Lưu vết từng lần click test (Thời gian, ai test, log lỗi)

3 Từ Điển Thuật Ngữ Kiểm Thử Chi Tiết

Hiển thị 28 / 28 thuật ngữ
Test Case (TC) Cốt Lõi
Trường hợp kiểm thử / Kịch bản kiểm thử

Tập hợp gồm các điều kiện tiên quyết (Preconditions), các bước thực hiện (Steps), dữ liệu đầu vào (Input Data) và kết quả mong đợi (Expected Result) nhằm xác định xem một tính năng cụ thể có hoạt động đúng theo yêu cầu phần mềm hay không.

Ví dụ đời thường: Giống như một tờ phiếu bài tập: Đề bài yêu cầu tính 2 + 2, đáp án chuẩn là 4. Bất kỳ ai cầm tờ phiếu này làm theo đều sẽ có cùng một tiêu chuẩn chấm điểm.
Developer Mapping
Bảng TestCases trong CSDL. Thuộc tính: Id, Code ("TC-001"), Title, SuiteId, Priority, Severity. Không có cột Result!
Test Step Chi Tiết
Bước kiểm thử

Một hành động nguyên tử (atomic action) bên trong Test Case. Mỗi bước luôn gồm 2 vế song song: Hành động thực hiện (Action) và Kết quả mong đợi tương ứng (Expected Outcome).

Ví dụ: Bước 1: Nhập email hợp lệ & click Next → Màn hình hiển thị ô nhập mật khẩu.
Bước 2: Nhập pass & click Đăng nhập → Chuyển hướng vào Dashboard, hiển thị avatar người dùng.
Developer Mapping
Bảng TestSteps. Khóa ngoại TestCaseId, thuộc tính StepOrder (int), Action (string), ExpectedResult (string).
Test Suite / Module Phân Cấp
Bộ kịch bản kiểm thử / Thư mục module

Cấu trúc cây thư mục dùng để nhóm các Test Case có liên quan logic lại với nhau (theo chức năng, theo microservice, hoặc theo hành trình người dùng). Ví dụ: Suite "Quản lý Đơn Hàng" chứa các sub-suite "Tạo đơn", "Thanh toán", "Hủy đơn".

Tương đương trong Code: Giống hệt cấu trúc Folder / Namespace trong dự án C# hay Java (Acme.Orders.Checkout).
Developer Mapping
Bảng TestSuites. Khóa ngoại tự trỏ ParentId (Guid?) để tạo cây thư mục vô tận, OrderIndex (int) để kéo thả sắp xếp (Drag & Drop).
TestCaseVersion Snapshot
Ảnh chụp đóng băng phiên bản kịch bản

Bản ghi bất biến (Immutable Record) lưu lại toàn bộ nội dung (Title, Precondition, Steps JSON) của Test Case tại một thời điểm cụ thể. Khi Test Case được cập nhật sang version mới (v2), các đợt test cũ đã chạy với v1 vẫn giữ nguyên vẹn giá trị lịch sử.

Tương đương trong Git: Giống như Git Commit Hash. Bạn có thể sửa code ở nhánh chính (master), nhưng commit lịch sử trong quá khứ không bao giờ bị thay đổi!
Developer Mapping
Bảng TestCaseVersions. Khóa ngoại TestCaseId, thuộc tính VersionNumber (int), SnapshotData (JSON string), CreatedTime.
Test Plan Kế Hoạch
Kế hoạch kiểm thử tổng thể

Văn bản / thực thể định nghĩa mục tiêu, phạm vi kiểm thử (Scope), tài nguyên, môi trường, thời hạn cho một đợt phát hành (Release) hoặc Milestone. Nó xác định: "Trong bản release v2.0 này, chúng ta sẽ test những Suite nào, những kịch bản nào?"

Ví dụ: Kế hoạch kiểm thử Sprint 24: Tập trung vào tính năng Cổng thanh toán MoMo và kiểm thử hồi quy luồng Đăng ký tài khoản.
Developer Mapping
Bảng TestPlans. Thuộc tính MilestoneId, StartDate, EndDate, Status (Draft/Active/Completed). Có thể chứa nhiều Test Runs bên trong.
Test Run Đợt Chạy
Đợt thực thi kiểm thử cụ thể

Một phiên làm việc thực tế để chạy một danh sách Test Case cụ thể trên một môi trường xác định (ví dụ: Chạy đợt test trên môi trường Staging - Trình duyệt Google Chrome hoặc Production - App iOS). Đây là nơi các tester bắt đầu click vào từng kịch bản để chấm điểm Pass/Fail.

Tương đương trong CI/CD: Giống như một Pipeline Run hay GitHub Actions Workflow Run.
Developer Mapping
Bảng TestRuns. Thuộc tính PlanId, Environment ("Staging"), AssignedToUserId, ExecutionStatus (Untested/In-Progress/Completed).
Test Run Item Phân Phối
Hạng mục kiểm thử trong đợt chạy

Thể hiện mối quan hệ gán (Instance) giữa một Test Case (chính xác hơn là một TestCaseVersion) với một Test Run. Nó đại diện cho 1 dòng công việc cụ thể: "Kịch bản Đăng nhập Google được đưa vào Đợt chạy Staging và gán cho bạn Tester A thực hiện".

Tương đương trong Jira: Giống như một Sub-task được tạo ra và assign cho một người thực hiện trong Sprint.
Developer Mapping
Bảng TestRunItems. Khóa ngoại TestRunId, TestCaseVersionId, AssignedUserId, CurrentStatus (Pass/Fail/Blocked/Untested - tính theo lần test mới nhất).
Test Execution Thực Thi
Lần thực thi / Ghi nhận kết quả (Attempt)

Nhật ký thực thi của một lần thử nghiệm cụ thể cho 1 Test Run Item. Khi tester bấm nút "Pass" hoặc "Fail", một bản ghi Test Execution mới được INSERT vào database. Nếu test lần 1 Fail, dev sửa bug, tester test lại lần 2 Pass → hệ thống có 2 bản ghi Execution liên kết với cùng 1 Run Item (Attempt 1 và Attempt 2).

Tương đương: Giống như Audit Log / Transaction Log. Chỉ INSERT thêm, không bao giờ UPDATE đè lên kết quả cũ!
Developer Mapping
Bảng TestExecutions. Khóa ngoại TestRunItemId, Status (Pass/Fail/Blocked), ActualResult, ExecutionTimeSeconds, ExecutedByUserId, ExecutedAt.
Test Scenario Tổng Quát
Kịch bản tổng quát / Tình huống kiểm thử

Mô tả ở mức tổng quan (high-level) về những gì cần kiểm tra, thường trả lời câu hỏi: "Cần kiểm tra cái gì?" (What to test), trong khi Test Case trả lời: "Kiểm tra như thế nào?" (How to test). Một Test Scenario thường sinh ra nhiều Test Case cụ thể.

Ví dụ: Scenario: "Kiểm tra chức năng Đăng nhập".
→ Sinh ra TC1: Login thành công với email hợp lệ (Happy path).
→ Sinh ra TC2: Login thất bại khi sai pass 5 lần (Lock account).
→ Sinh ra TC3: Login bằng tài khoản chưa kích hoạt.
Developer Mapping
Thường tương đương với một User Story hoặc một Feature Acceptance Criteria trong Jira.
Pre & Post Condition Điều Kiện
Tiền điều kiện & Hậu điều kiện

Precondition: Trạng thái bắt buộc của hệ thống hoặc dữ liệu trước khi bắt đầu test (ví dụ: User đã đăng nhập, giỏ hàng đang có ít nhất 1 sản phẩm).
Postcondition: Trạng thái của hệ thống sau khi test xong (ví dụ: Số lượng tồn kho giảm 1, đơn hàng chuyển sang trạng thái "Đã thanh toán").

Tương đương trong Unit Test: Giống như hàm [SetUp] (khởi tạo mock data) và [TearDown] (dọn dẹp dữ liệu/rollback transaction).
Developer Mapping
Thuộc tính Preconditions (string) và Postconditions (string) trong bảng TestCases.
Expected vs Actual So Sánh
Kết quả mong đợi vs Kết quả thực tế

Expected Result: Kết quả được định nghĩa từ trước theo tài liệu đặc tả (SRS/Figma).
Actual Result: Kết quả thực tế hiển thị trên màn hình khi tester chạy ứng dụng.
→ Nếu Expected == Actual → PASS.
→ Nếu Expected != Actual → FAIL (Phát hiện Bug!).

Tương đương trong Code: Giống như câu lệnh Assert.Equal(expected, actual); trong thư viện xUnit / NUnit.
Developer Mapping
ExpectedResult nằm ở bảng mẫu TestSteps; còn ActualResult nằm ở bảng thực thi TestExecutions.
RTM Truy Vết
Requirements Traceability Matrix (Ma trận truy vết)

Ma trận 2 chiều liên kết giữa Yêu cầu nghiệp vụ (User Story / Requirement) với các Test Case kiểm thử nó và các Bug phát sinh. Giúp trả lời câu hỏi cốt tử của sếp: "Tính năng Đổi mật khẩu này đã có kịch bản test chưa? Test bao nhiêu case? Đã Pass hết chưa?"

Góc nhìn Dev: Giống như đo đạc Code Coverage, nhưng ở cấp độ Nghiệp vụ (Business Requirement Coverage).
Developer Mapping
Bảng trung gian N-N: RequirementTestCases (RequirementId & TestCaseId). Dùng để xuất báo cáo Coverage %.
Quality Gate Cổng Xuất Xưởng
Cổng kiểm soát chất lượng (Release Gate)

Tập hợp các tiêu chí định lượng (Thresholds) bắt buộc phải đạt được trước khi một bản build được phép triển khai (Deploy) lên môi trường tiếp theo (ví dụ: từ Staging lên Production).
Ví dụ: Tỷ lệ Pass rate ≥ 95%, 0 Bug Critical/High còn mở, 100% Smoke tests hoàn thành.

Tương đương trong CI/CD: Giống như quy tắc chặn merge PR (Merge Rules): Bắt buộc CI test passed, SonarQube Quality Gate passed mới cho click Merge!
Developer Mapping
Logic kiểm tra tự động trước khi đóng Test Plan: if (failedCriticalBugs > 0 || passRate < 0.95) return BlockRelease();
Flaky Test Chập Chờn
Kịch bản kiểm thử không ổn định (Heisenbug)

Một test case mà khi chạy lặp đi lặp lại trên cùng một phiên bản mã nguồn (source code không đổi) nhưng lúc thì Pass, lúc lại Fail. Nguyên nhân phổ biến: mạng chập chờn, bất đồng bộ (Race condition), phụ thuộc thứ tự test, hoặc dữ liệu test bị trùng lặp.

Nỗi đau của Dev: Cảm giác tức tối khi CI/CD lúc đỏ lúc xanh không rõ nguyên nhân khiến team mất niềm tin vào hệ thống kiểm thử tự động.
Developer Mapping
Cột IsFlaky (bool) và FlakyScore (double) trong bảng TestCases. Tự động tính toán khi kết quả đảo chiều liên tục giữa các lần chạy.
Severity vs Priority Phân Loại Lỗi
Độ nghiêm trọng kỹ thuật vs Độ ưu tiên kinh doanh

Severity (Nghiêm trọng): Mức độ ảnh hưởng kỹ thuật của lỗi lên hệ thống (Crash app, mất dữ liệu, rò rỉ bảo mật).
Priority (Ưu tiên): Mức độ khẩn cấp cần phải sửa xét theo góc độ kinh doanh và người dùng (Cần fix ngay hôm nay hay để tuần sau).

Ví dụ kinh điển: Logo công ty bị sai chính tả thành từ ngữ nhạy cảm ngay trang chủ → Severity Thấp (không crash hệ thống), nhưng Priority Cực Cao (phải sửa trong 5 phút vì ảnh hưởng thương hiệu!).
Developer Mapping
Hai enum độc lập: SeverityLevel { Low, Medium, High, Critical } và PriorityLevel { Low, Medium, High, Urgent }.
Smoke Testing Test Khói
Kiểm thử sơ bộ / Build Acceptance Test

Đợt kiểm thử nhanh các tính năng sống còn cốt lõi nhất ngay sau khi nhận bản build mới. Mục đích: Kiểm tra xem hệ thống có "bốc khói" (crash màn hình, không mở được app, không login được) hay không. Nếu Smoke Test fail → Từ chối bản build ngay lập tức, không tốn công test tiếp!

Nguồn gốc: Lấy từ ngành sửa ống nước/điện tử: Khi cắm điện vào bảng mạch mới lắp, nếu thấy bốc khói thì lập tức rút điện ra sửa, chưa cần đo đạc gì phức tạp.
Developer Mapping
Cột gắn cờ IsSmokeTest (bool) trên TestCases. Dùng để tạo Test Run nhanh trong CI/CD chỉ gồm ~10-20 case tối quan trọng.
Sanity Testing Tỉnh Táo
Kiểm thử nhanh vùng vừa sửa lỗi

Đợt kiểm thử tập trung vào một phân hệ hẹp vừa mới được Dev sửa bug hoặc thêm một tính năng nhỏ. Mục đích: Xác nhận xem Dev có thực sự sửa đúng bug đó chưa và hệ thống có còn "tỉnh táo" (sane) ở khu vực đó không. Khác với Smoke test (rộng và nông), Sanity test là (hẹp và sâu vào tính năng vừa sửa).

Ví dụ: Dev vừa báo: "Đã sửa bug lỗi mã giảm giá 50%". Tester mở đúng form nhập mã giảm giá ra test các trường hợp mã → Đó là Sanity Test.
Developer Mapping
Test Run được tạo theo BugId hoặc nhánh hotfix cụ thể.
Regression Testing Hồi Quy
Kiểm thử hồi quy

Việc chạy lại các kịch bản kiểm thử đã có từ trước sau khi mã nguồn có sự thay đổi (thêm tính năng mới, refactor code, nâng cấp thư viện). Mục đích tối thượng: Đảm bảo những tính năng cũ đã chạy tốt KHÔNG BỊ HỎNG bởi những dòng code mới!

Quy luật đau đớn: "Sửa 1 dòng code ở module A, vô tình làm nổ tung module B". Kiểm thử hồi quy chính là tấm lưới bắt các vụ nổ ngầm này.
Developer Mapping
Tập hợp các Test Case được đánh dấu IsRegression (bool). Đây là tập kịch bản lý tưởng nhất để viết kiểm thử tự động (Automation Test).
UAT (User Acceptance) Nghiệm Thu
Kiểm thử chấp nhận của người dùng

Giai đoạn kiểm thử cuối cùng trước khi bàn giao hệ thống, do chính khách hàng, người dùng cuối (End-user) hoặc Product Owner (PO) trực tiếp thực hiện. Mục đích: Kiểm tra xem hệ thống có giải quyết đúng bài toán nghiệp vụ của họ trong thực tế hay không, thay vì chỉ kiểm tra đúng code.

Ví dụ: Dev làm đúng theo thiết kế, app không có lỗi kỹ thuật nào, nhưng khách hàng bảo: "Thao tác thanh toán phải bấm tới 7 bước thì nhân viên bán hàng của tôi không dùng kịp".
Developer Mapping
Một Test Plan riêng biệt gán cho nhóm người dùng mang Role Client / BusinessTester.
Defect Link Liên Kết Lỗi
Liên kết lỗi sang hệ thống Issue Tracker

Cơ chế đồng bộ 2 chiều giữa kết quả thất bại (Failed Execution) trong hệ thống TCM với một vé lỗi (Bug Ticket) trên các công cụ quản lý công việc như Jira, GitHub Issues, Azure DevOps, GitLab. Giúp Dev click từ Jira là xem được ngay các bước tái hiện và ảnh chụp màn hình lúc test.

Tương đương: Giống như một External Foreign Key nối từ bảng TestExecutions sang Jira Issue Key (ví dụ: PROJ-1234).
Developer Mapping
Bảng DefectLinks. Thuộc tính TestExecutionId, ExternalSystem ("Jira"), ExternalIssueKey ("PROJ-89"), ExternalUrl.
Sign-Off Report Biên Bản
Biên bản nghiệm thu xuất xưởng

Báo cáo tổng hợp trang trọng được xuất ra khi hoàn thành một Test Plan. Chứa đầy đủ số liệu: Tổng số case đã chạy, tỷ lệ Pass/Fail, danh sách các Bug còn tồn đọng (Known Issues) và chữ ký điện tử phê duyệt của QA Lead, Tech Lead và Product Owner cho phép release sản phẩm.

Ý nghĩa pháp lý: Là "giấy thông hành" chính thức giải phóng trách nhiệm cho team Dev và QA khi bản cập nhật được đẩy lên Production.
Developer Mapping
Bảng TestSignOffs. Thuộc tính TestPlanId, SummaryStatsJson, Decision (Approved/Rejected), ApprovedByUserId, SignOffDate.
Automation ID Tự Động Hóa
Mã định danh liên kết kịch bản tự động

Chuỗi định danh duy nhất (Unique Key) dùng để nối một Test Case thủ công trên giao diện web với một hàm kiểm thử tự động trong mã nguồn (viết bằng Playwright, Selenium, Cypress, xUnit). Khi CI/CD chạy xong, nó dùng ID này để tự động đẩy kết quả Pass/Fail ngược vào hệ thống TCM thông qua REST API.

Ví dụ trong code: [Fact(DisplayName = "TC-LOGIN-001")] → CI runner parse kết quả XML/JSON và gửi API: "Cập nhật kết quả cho AutomationId = TC-LOGIN-001 là PASS".
Developer Mapping
Cột AutomationId (string, Indexed) và enum ExecutionType { Manual, Automated, Hybrid } trong TestCases.
Positive vs Negative Kỹ Thuật
Kiểm thử tích cực vs Kiểm thử tiêu cực

Positive Testing (Happy Path): Nhập dữ liệu hợp lệ và kỳ vọng hệ thống thực hiện đúng chức năng (ví dụ: Nhập đúng mật khẩu → Đăng nhập thành công).
Negative Testing (Unhappy Path): Cố tình nhập dữ liệu sai, bất thường, độc hại và kỳ vọng hệ thống xử lý lỗi khéo léo (graceful error handling) thay vì sập web (ví dụ: Nhập ký tự SQL Injection, để trống ô bắt buộc).

Dev chú ý: Dev thường chỉ chăm chăm viết code cho Happy Path, còn QA sinh ra là để "phá hoại" bằng Negative Testing nhằm bảo vệ hệ thống.
Developer Mapping
Cột TestKind (Enum: Positive, Negative, Boundary) trong bảng TestCases.
BVA (Giá Trị Biên) Thiết Kế
Boundary Value Analysis (Phân tích giá trị biên)

Kỹ thuật thiết kế test case dựa trên quy luật thực nghiệm: Hầu hết lỗi lập trình đều xảy ra tại các điểm biên của điều kiện (lỗi kinh điển Off-by-one: > thay vì ≥).
Nếu ô nhập tuổi cho phép từ 18 đến 60, các giá trị cần test gồm: 17, 18, 19 và 59, 60, 61.

Mẹo cho Dev: Khi viết câu lệnh if (age >= 18 && age <= 60), hãy tự viết unit test tại các điểm 17, 18, 60, 61 trước khi nộp code!
Developer Mapping
Dùng để thiết kế các kịch bản test kiểm tra validation logic của DTO trong FluentValidation.
Equivalence Partitioning Thiết Kế
Phân vùng tương đương

Kỹ thuật chia tập dữ liệu đầu vào thành các nhóm (vùng) có tính chất xử lý giống nhau. Nếu một giá trị đại diện trong nhóm hoạt động đúng/sai, thì tất cả các giá trị khác trong nhóm đó cũng sẽ hoạt động tương tự. Giúp giảm số lượng test case từ hàng ngàn xuống còn vài case đại diện.

Ví dụ: Ô nhập điểm thi từ 0 đến 10. Chia làm 3 vùng: Vùng hợp lệ (0-10, chọn số 7 để test), Vùng âm (< 0, chọn -5 để test), Vùng vượt quá (> 10, chọn 15 để test).
Developer Mapping
Phương pháp thiết kế bảng dữ liệu kiểm thử (Test Data Matrix).
Black-box vs White-box Phương Pháp
Hộp đen vs Hộp trắng

Hộp đen (Black-box): Tester hoàn toàn không biết cấu trúc code bên trong, chỉ thao tác qua giao diện UI/API như một người dùng thông thường.
Hộp trắng (White-box): Kiểm thử dựa trên việc nhìn thấy mã nguồn, kiểm tra từng rẽ nhánh (branch coverage), từng dòng lệnh (Dev viết Unit Test chính là White-box testing).

Ẩn dụ: Lái thử một chiếc ô tô xem chạy êm không (Hộp đen) vs Mở nắp capo xem từng pít-tông và dây điện hoạt động ra sao (Hộp trắng).
Developer Mapping
Cột TestingMethod { BlackBox, WhiteBox, GrayBox } trong thuộc tính mở rộng của TestCase.
Shared / Reusable Step Tái Sử Dụng
Bước kiểm thử dùng chung

Một tập hợp các bước kiểm thử được định nghĩa một lần nhưng được nhúng vào nhiều Test Case khác nhau. Ví dụ: Bước "Đăng nhập với quyền Quản trị viên" xuất hiện ở 200 kịch bản khác nhau. Khi đổi giao diện đăng nhập, chỉ cần sửa 1 lần tại Shared Step là 200 kịch bản tự động cập nhật theo!

Tương đương trong Code: Giống hệt việc viết một hàm dùng chung (Helper Function / Sub-routine) thay vì copy-paste code ra 200 chỗ.
Developer Mapping
Bảng SharedSteps. Trong bảng TestSteps có cột SharedStepId (Guid?) để trỏ tới.
Milestone Cột Mốc
Cột mốc dự án / Mục tiêu phát hành

Cột mốc thời gian hoặc sự kiện bàn giao quan trọng trong dự án (ví dụ: "Bản Alpha Release", "Sprint 14 Review", "UAT Khách hàng đợt 1"). Một Milestone thường là thực thể cha, chứa nhiều Test Plan và Test Run bên dưới để theo dõi tiến độ tổng thể.

Tương đương: Giống như Milestone trong GitHub hoặc Release Version trong Jira.
Developer Mapping
Bảng Milestones. Thuộc tính Name, TargetDate, IsCompleted. 1 Milestone có quan hệ 1-N với TestPlans.

4 Đại Chiến Phân Biệt: Các Cặp Khái Niệm Dễ Nhầm Lẫn Nhất

Head-to-Head Comparison

Dưới đây là 4 cặp khái niệm mà 95% lập trình viên khi mới làm quen với QA đều bị nhầm lẫn hoặc dùng sai thuật ngữ:

Test Plan vs Test Run
VS
Test Plan
  • Ý nghĩa: Kế hoạch phạm vi (Scope). Trả lời: Sẽ test cái gì trong Sprint này?
  • Tần suất: Tạo 1 lần cho cả Sprint hoặc Release.
  • Chứa đựng: Chứa nhiều Test Run bên dưới.
Test Run
  • Ý nghĩa: Đợt thực thi cụ thể. Trả lời: Đang chạy trên môi trường nào, ai test?
  • Tần suất: Tạo liên tục theo từng build/môi trường.
  • Chứa đựng: Chứa danh sách các Test Run Item & kết quả thực tế.
Công thức nhớ cho Dev: TestPlan là Giỏ hàng dự kiến; TestRun là Hóa đơn thanh toán thực tế của từng lần mua.
Test Scenario vs Test Case
VS
Test Scenario
  • Góc nhìn: Tổng quan, High-level.
  • Trả lời: Test cái gì? (Ví dụ: Kiểm tra việc chuyển tiền qua app).
  • Độ chi tiết: Không có bước bấm cụ thể, không có dữ liệu test chi tiết.
Test Case
  • Góc nhìn: Chi tiết, Low-level.
  • Trả lời: Test như thế nào? (Click nút nào, nhập số tiền mấy, thông báo gì hiện ra).
  • Độ chi tiết: Có Precondition, Step 1..n, Expected Result.
Quan hệ: 1 Test Scenario sinh ra N Test Cases (1 tình huống có nhiều ca kiểm thử thành công, thất bại, biên).
Test Run Item vs Test Execution
VS
Test Run Item
  • Là gì: Nhiệm vụ gán test (Assignment). 1 dòng trong bảng chạy test.
  • Số lượng: Duy nhất 1 bản ghi cho mỗi Test Case trong một Test Run.
  • Trạng thái: Thể hiện trạng thái mới nhất (Pass hoặc Fail).
Test Execution
  • Là gì: Lịch sử của từng lần bấm thử (Attempt).
  • Số lượng: Có thể có nhiều bản ghi (Lần 1 Fail, Lần 2 Blocked, Lần 3 Pass).
  • Tính chất: Bất biến (Immutable Log), không bao giờ bị ghi đè.
Công thức nhớ: Quan hệ 1 - N. Một nhiệm vụ (Item) có thể phải làm lại (Execution) nhiều lần mới đạt yêu cầu.
Smoke vs Sanity vs Regression
VS
Smoke & Sanity
  • Smoke Test: Rộng nhưng Nông. Chạy nhanh ~15 phút xem app có khởi động được không.
  • Sanity Test: Hẹp nhưng Sâu. Chỉ kiểm tra riêng tính năng vừa sửa bug.
Regression
  • Quy mô: Toàn diện và Sâu rộng.
  • Mục tiêu: Đảm bảo code mới không làm hỏng tính năng cũ.
  • Thời gian: Thường mất vài giờ đến vài ngày (hoặc chạy automation qua đêm).
Trình tự thực tế: Nhận build → Chạy Smoke (nếu sống) → Chạy Sanity (check bug vừa sửa) → Chạy Regression (check toàn bộ hệ thống).

5 Các Cấp Độ & Loại Hình Kiểm Thử Dev Cần Nắm

Testing Levels & Types

Trong kim tự tháp kiểm thử phần mềm (Testing Pyramid), trách nhiệm kiểm thử được phân chia rõ rệt giữa Dev và QA:

Cấp độ Kiểm thử Ai là người thực hiện? Công cụ / Ngôn ngữ phổ biến Mục tiêu chính
1. Unit Testing (Cấp đơn vị) 100% Lập trình viên xUnit, NUnit, Jest, JUnit, Moq Kiểm tra từng hàm, từng class riêng lẻ với dữ liệu mock cách ly hoàn toàn.
2. Integration Testing (Tích hợp) Dev & Automation QA TestServer, Testcontainers, Postman Kiểm tra kết nối thực tế giữa API, Database, Redis Cache, Message Queue.
3. System Testing (Hệ thống) QA / QC Team TCM Platform (TestRail, Phần mềm bạn đang làm), Browser Kiểm thử toàn diện phần mềm hoàn chỉnh theo kịch bản người dùng cuối.
4. Acceptance Testing (Nghiệm thu) Khách hàng, PO, End-User UAT Environment, Test Scenarios Xác nhận sản phẩm đáp ứng đúng giá trị nghiệp vụ trước khi thanh toán hợp đồng.

6 Lược Đồ Cơ Sở Dữ Liệu & Code C# Chuẩn ABP Framework

C# & EF Core Domain Entities

Dưới đây là cách mô hình hóa các thực thể cốt lõi bằng C# theo chuẩn Domain-Driven Design (DDD) và ABP Framework, đảm bảo tách bạch hoàn hảo giữa Thư viện kịch bản và Đợt chạy: 

// ============================================================================
// 1. KHO THƯ VIỆN KỊCH BẢN (DESIGN-TIME REPOSITORY)
// ============================================================================

// Aggregate Root quản lý thông tin chung của Test Case
public class TestCase : FullAuditedAggregateRoot<Guid>
{
    public Guid SuiteId { get; set; }           // Thuộc về Test Suite (Folder) nào
    public string Code { get; set; }             // Mã kịch bản (VD: "TC-AUTH-001")
    public string Title { get; set; }            // Tiêu đề tóm tắt
    public PriorityLevel Priority { get; set; }  // Low, Medium, High, Urgent
    public SeverityLevel Severity { get; set; }  // Low, Medium, High, Critical
    public ExecutionType Type { get; set; }      // Manual, Automated, Hybrid
    public string? AutomationId { get; set; }    // Định danh để tool test tự động mapping
    public bool IsFlaky { get; set; }            // Có bị chập chờn hay không
    
    // Lưu ý: Không hề có trường Result hay Status ở đây!
}

// Bảng đóng băng phiên bản (Immutable Snapshot)
public class TestCaseVersion : CreationAuditedEntity<Guid>
{
    public Guid TestCaseId { get; set; }
    public int VersionNumber { get; set; }       // v1, v2, v3
    public string Title { get; set; }
    public string Preconditions { get; set; }    // Điều kiện tiên quyết
    public string StepsJson { get; set; }        // Snapshot toàn bộ các bước dạng JSON
    public string Postconditions { get; set; }
}

// ============================================================================
// 2. CHU KỲ THỰC THI KIỂM THỬ (EXECUTION-TIME RUN CYCLE)
// ============================================================================

// Kế hoạch tổng thể cho 1 Sprint hoặc Release
public class TestPlan : FullAuditedAggregateRoot<Guid>
{
    public string Name { get; set; }             // "Test Plan Sprint 24"
    public Guid? MilestoneId { get; set; }
    public DateTime? StartDate { get; set; }
    public DateTime? EndDate { get; set; }
    public PlanStatus Status { get; set; }       // Draft, InProgress, Closed
}

// Một đợt chạy cụ thể trên 1 môi trường xác định
public class TestRun : FullAuditedAggregateRoot<Guid>
{
    public Guid TestPlanId { get; set; }
    public string Title { get; set; }            // "Chạy kiểm thử Staging - Chrome 124"
    public string Environment { get; set; }      // "Staging", "Production", "iOS 17"
    public Guid? AssignedToUserId { get; set; }
    public RunStatus Status { get; set; }        // New, InProgress, Completed
}

// Một hạng mục test cụ thể trong đợt chạy (Instance)
public class TestRunItem : Entity<Guid>
{
    public Guid TestRunId { get; set; }
    public Guid TestCaseVersionId { get; set; }  // Trỏ thẳng vào Snapshot bất biến!
    public Guid? AssignedUserId { get; set; }
    public TestResultStatus CurrentStatus { get; set; } // Untested, Passed, Failed, Blocked
}

// Lịch sử từng lần tester bấm test (Attempt log - 1 Item có N lần Executions)
public class TestExecution : CreationAuditedEntity<Guid>
{
    public Guid TestRunItemId { get; set; }
    public TestResultStatus Status { get; set; } // Passed, Failed, Blocked
    public string? ActualResult { get; set; }     // Thực tế hiển thị gì khi bị lỗi
    public int DurationSeconds { get; set; }     // Thời gian thực hiện test (giây)
    public string? DefectJiraKey { get; set; }   // Nếu lỗi: link sang "PROJ-102"
    // Khi Re-test: INSERT bản ghi mới, KHÔNG BAO GIỜ UPDATE dòng cũ!
}

7 Thử Thách Lập Trình Viên: Mini-Quiz Khái Niệm Kiểm Thử

5 Câu hỏi tương tác

Hãy kiểm tra xem bạn đã thực sự "thông suốt" các khái niệm kiểm thử phần mềm qua 5 câu trắc nghiệm nhanh dưới đây:

1 Khi thiết kế CSDL cho hệ thống Test Case Management, cột Status (Passed/Failed) nên được đặt ở bảng nào là đúng chuẩn nhất?
A. Đặt trực tiếp vào bảng TestCases để truy vấn cho nhanh.
B. Đặt ở bảng TestExecutions (nhật ký thực thi) và cập nhật trạng thái mới nhất ở TestRunItems.
C. Đặt vào bảng TestSuites để hiển thị cây thư mục.
D. Đặt vào bảng TestPlans.
Giải thích: Chính xác! Bảng TestCases chỉ là thư viện kịch bản dùng chung lâu năm. Kết quả Pass/Fail phải gắn liền với một đợt chạy cụ thể (TestRunItems) và từng lần bấm thử (TestExecutions).
2 Một test case mà khi chạy trên cùng một bản build mã nguồn nhưng lúc thì PASS, lúc thì FAIL được gọi là gì?
A. Smoke Test.
B. Flaky Test.
C. Regression Test.
D. Sanity Test.
Giải thích: Chính xác! Flaky Test (Test chập chờn) là cơn ác mộng lớn nhất trong CI/CD, thường do race condition, timeout hoặc bất đồng bộ gây ra.
3 Website bị lỗi sai chính tả từ ngữ nhạy cảm ngay trên Logo trang chủ (nhưng website không hề bị crash). Phân loại lỗi này như thế nào?
A. Severity: Critical, Priority: Low.
B. Severity: Low (kỹ thuật nhẹ), Priority: High / Urgent (kinh doanh khẩn cấp).
C. Severity: Critical, Priority: Critical.
D. Severity: Low, Priority: Low.
Giải thích: Rất chuẩn! Về mặt kỹ thuật hệ thống hoàn toàn bình thường (Severity Low), nhưng về mặt thương hiệu và trải nghiệm khách hàng thì cực kỳ khẩn cấp cần sửa ngay lập tức (Priority Urgent).
4 Tại sao hệ thống TCM bắt buộc phải có cơ chế TestCaseVersion (Snapshot)?
