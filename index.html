1 Bối Cảnh Dự Án, Động Lực Tự Xây Dựng & Phân Kỳ MVP

1.1. Thực trạng & Điểm đau (Pain Points) thực tế của đội ngũ

Trong các dự án phần mềm doanh nghiệp, hoạt động kiểm thử thường đối mặt với các nút thắt cổ chai lớn:

Phân Mảnh & Nhân Bản Excel Bừa Bãi

Mỗi đợt Release hoặc Sprint lại nhân bản một file Excel mới. Khi yêu cầu thay đổi, kịch bản gốc trong sheet mẫu không được cập nhật; ngược lại, các đợt test cũ bị mất dấu theo dõi.

Ghi Đè Kết Quả (Retest Overwrite)

Khi chạy lần 1 bị Failed → Dev sửa → Tester test lại và sửa trạng thái thành Passed. Bằng chứng, log lỗi và thời gian của lần chạy đầu tiên bị xóa sạch, không đo được độ bất ổn định (Flaky rate).

Lệch Pha Nội Dung Phiên Bản (Version Drift)

Sửa test case giữa chừng làm thay đổi các bước của đợt Test Run cũ đang thực hiện hoặc đã đóng, khiến biên bản nghiệm thu (Sign-off) bị sai khác so với thực tế lúc test.

Mù Mờ Tiến Độ Nghiệm Thu Release

PO và PM không có Dashboard trực quan thời gian thực, không biết hôm nay đã chạy bao nhiêu case, còn nghẽn (Block) ở đâu để kịp thời điều phối nguồn lực.

1.2. Tại sao tự xây dựng Module trên ABP thay vì dùng SaaS (TestRail, Zephyr, Qase)?

  • Chủ quyền dữ liệu & Tuân thủ On-Premise/Private Cloud: Các dự án ngân hàng, tài chính, khối nhà nước bắt buộc lưu trữ dữ liệu tại máy chủ nội bộ, nghiêm cấm tải kịch bản nghiệp vụ và bug lên các nền tảng SaaS Cloud nước ngoài.
  • Tối ưu chi phí bản quyền lâu dài: Chi phí TestRail (~$37/user/tháng) hoặc Zephyr cho team 30–50 người tiêu tốn hàng chục nghìn USD mỗi năm. Việc đóng gói thành 1 module ABP dùng chung cho toàn bộ hệ sinh thái của công ty giúp tiết kiệm 100% chi phí này.
  • Tích hợp sâu vào hệ sinh thái ABP nội bộ: Dùng chung hệ thống phân quyền (Permission), Single Sign-On (SSO), Audit Logging, và quy trình phê duyệt sẵn có của doanh nghiệp.
  • Khả năng tùy biến linh hoạt: Tự do tích hợp luồng webhook nội bộ, server automation test riêng, hoặc kết nối hệ thống Task nội bộ mà không phụ thuộc API bên ngoài.

1.3. Phân kỳ phạm vi rõ ràng (MVP Scoping)

Giai đoạn Mục tiêu cốt lõi Phạm vi chức năng cụ thể
Pha 1 (MVP) Đủ để đội ngũ QA thay thế hoàn toàn Excel trong 1 dự án cụ thể. • Cây thư viện Module → Test Case (không gán Sprint vào cây thư viện).
• Soạn thảo Test Case (Priority, Kind, Layer, Tags, Steps).
• Vòng đời phê duyệt: Draft → In Review → Approved / Rejected.
• Snapshot phiên bản (TestCaseVersion) khi chạy test.
• Tạo Test Plan / Test Run gắn Milestone/Sprint.
• Ghi nhận kết quả theo nhiều lần chạy (TestExecution History: Run 1 Fail, Run 2 Pass).
• Báo cáo tiến độ Pass/Fail thời gian thực & Biên bản nghiệm thu (Sign-Off).
Pha 2 Mở rộng cho nhiều dự án & tự động hóa tích hợp. • Nhập/xuất dữ liệu Excel/CSV tương thích mẫu cũ.
• Liên kết Bug Defect hai chiều sang Jira/GitHub/Redmine qua Webhook.
• Báo cáo Ma trận truy vết yêu cầu (Requirement Traceability Matrix - RTM).
• Realtime sync tiến độ đợt test bằng SignalR Hub & In-app/Email Notifications.
Pha 3 Hợp nhất tự động hóa CI/CD & AI Trợ Lý. • REST API nạp kết quả tự động từ Playwright/Cypress/JUnit XML qua AutomationId.
• Tích hợp AI (Semantic Kernel) hỗ trợ sinh kịch bản từ User Story / AC.
• AI phát hiện test trùng lặp qua Vector Embedding & Smart Regression Selection.

2 Các Đối Tượng Nghiệp Vụ & Phân Quyền (Actors & Permissions)

2.1. Ma trận trách nhiệm RACI chuẩn hóa

R: Responsible (Thực hiện) | A: Accountable (Chịu trách nhiệm chính) | C: Consulted (Tham vấn) | I: Informed (Nhận thông tin)

Hoạt động nghiệp vụ QA Lead / Manager QA Tester Developer Product Owner / BA
1. Thiết kế & Soạn thảo Test Case A R C C
2. Thẩm định & Duyệt (Approve/Reject) A / R I I C
3. Lập Test Plan & Test Run (gắn Sprint) A / R I I I
4. Phân công & Thực thi Test Run A R I I
5. Đóng Test Run & Ký nghiệm thu A / R C I A

2.2. Danh mục Quyền hạn (ABP Permissions) độc lập của Module

Module tự đăng ký nhóm quyền riêng biệt TestCaseManagement vào hệ thống phân quyền ABP:

Dự án & Thư viện Test Case

  • TestCaseManagement.Projects.Manage: Tạo/sửa cấu hình dự án, Quality Gate
  • TestCaseManagement.TestCases.Create: Soạn thảo kịch bản Draft
  • TestCaseManagement.TestCases.Edit: Chỉnh sửa kịch bản đang mở
  • TestCaseManagement.TestCases.Delete: Xóa bản nháp (Draft)
  • TestCaseManagement.TestCases.Approve: Phê duyệt hoặc Từ chối kịch bản (QA Lead)

Kế hoạch, Đợt Test & Báo cáo

  • TestCaseManagement.TestPlans.Create/Edit/Delete: Quản lý kế hoạch test
  • TestCaseManagement.TestRuns.Create: Tạo đợt chạy test gắn Milestone
  • TestCaseManagement.TestRuns.Execute: Chạy test & ghi nhận kết quả (Tester)
  • TestCaseManagement.TestRuns.Close: Khóa đợt test & ký nghiệm thu (QA Lead)
  • TestCaseManagement.Reports.View / Export: Xem Dashboard, xuất PDF/Excel

3 Thiết Kế Quy Trình Nghiệp Vụ Chuẩn Xác

Nguyên Tắc Vàng Tách Rời: Kho Thư Viện vs. Đợt Thực Thi

Cây Thư Viện Kịch Bản (Test Repository): Đại diện cho tài sản vĩnh cửu theo cấu trúc tính năng của phần mềm: Dự án → Phân hệ (Module) → Nhóm chức năng (Suite) → Test Case. Tuyệt đối KHÔNG đưa Sprint/Milestone vào cây thư viện vì kịch bản phải được tái sử dụng liên tục qua nhiều Sprint và bản Release.
Kế Hoạch & Đợt Chạy (Test Plan / Test Run): Là ngữ cảnh thực thi theo thời gian. Sprint, Milestone, Môi trường kiểm thử (Staging, Prod), Build Version chỉ thuộc về TestPlan và TestRun.

6 Quy Tắc Nghiệp Vụ Chuẩn Hóa (Business Rules Catalog)

Hệ thống quy tắc bất di bất dịch đảm bảo tính toàn vẹn dữ liệu, chống sai sót vận hành và bảo vệ số liệu kiểm toán:

6.1. Quy tắc về Test Case (BR-TC)

Mã Quy tắc nghiệp vụ Hành động hệ thống khi vi phạm
BR-TC-01 Test Case phải có ít nhất 1 bước kiểm thử (TestStep). Chặn Submit for Review nếu Steps rỗng. Trả validation error.
BR-TC-02 Mã Code tự sinh theo format {ProjectCode}-{AutoIncrement} (vd: BANK-001). Hệ thống tự tăng qua Sequence DB, cấm người dùng sửa tay.
BR-TC-03 Mã Code phải duy nhất (Unique) trong toàn bộ Project. Unique constraint trong CSDL, ném BusinessException nếu trùng.
BR-TC-04 Test Case ở trạng thái InReview không được chỉnh sửa nội dung. Khóa giao diện form soạn thảo. API trả HTTP 403 Forbidden.
BR-TC-05 Test Case Approved chỉ được chuyển về Draft để sửa, hoặc Deprecated. Cấm xóa. Ẩn nút Delete. Chỉ cho phép hành động "Tạo bản nháp chỉnh sửa".
BR-TC-06 Chỉ Test Case có trạng thái Approved mới được thêm vào Test Run. Bộ lọc thêm case chỉ hiển thị case Approved. Chặn API nếu gửi case Draft.
BR-TC-07 Khi Approved, hệ thống tự động sinh TestCaseVersion mới và tăng ActiveVersionNumber. Thực hiện trong Domain Service TestCaseManager.ApproveAsync().
BR-TC-08 Severity KHÔNG tồn tại trong Test Case. Severity chỉ thuộc DefectLink. Không khai báo trường Severity trong Entity TestCase.
BR-TC-09 Cây thư viện Test Case KHÔNG chứa Sprint / Milestone. Entity Module không có trường MilestoneId.

6.2. Quy tắc về TestCaseVersion (Bất Biến)

Mã Quy tắc nghiệp vụ Hành động hệ thống khi vi phạm
BR-VER-01 TestCaseVersion là bản chụp bất biến (Immutable Snapshot). Sau khi tạo cấm sửa đổi. Không cung cấp API Update. Entity không có public setter cho dữ liệu.
BR-VER-02 Chứa đầy đủ snapshot: Title, Preconditions, Priority, Kind, Layer, Tags và toàn bộ Steps. Snapshot JSON hóa ngay lúc phê duyệt, kiểm tra null trước khi insert.

6.3. Quy tắc về Test Plan / Test Run / Execution (BR-RUN)

Mã Quy tắc nghiệp vụ Hành động hệ thống khi vi phạm
BR-RUN-01 TestRunItem bắt buộc phải liên kết tới TestCaseVersionId. Không được null. Foreign Key NOT NULL. Tự động lấy ActiveVersion lúc thêm vào Run.
BR-RUN-02 Khi Test Run ở trạng thái Completed/Archived: cấm thực thi, cấm sửa kết quả. Khóa toàn bộ quyền thao tác. Trả lỗi "Test Run is locked for audit".
BR-RUN-03 Mỗi TestExecution có AttemptNumber tự tăng (1, 2, 3...). Không xóa lần cũ. Tự động tính MAX(AttemptNumber) + 1. Cấm API xóa execution.
BR-RUN-04 CurrentStatus của Item luôn phản ánh kết quả lần chạy cuối cùng. Domain Event cập nhật TestRunItem.CurrentStatus = LatestExecution.Status.
BR-RUN-05 Quality Gate: Chỉ cho phép Close Run khi đạt tiêu chí cấu hình (100% P1 Pass, 0 Blocker). Cảnh báo No-Go nếu chưa đạt. Yêu cầu nhập lý do Override nếu cố đóng.
BR-RUN-06 Milestone chỉ thuộc về TestPlan/TestRun, không thuộc cây thư viện. TestPlan lưu MilestoneId; cây Module độc lập với thời gian.

6.4. Quy tắc về Module Cây Thư Viện & File Đính Kèm (BR-MOD & BR-ATT)

Mã Quy tắc nghiệp vụ Hành động hệ thống khi vi phạm
BR-MOD-01 Cây phân cấp Module hỗ trợ tối đa 5 cấp lồng nhau. Kiểm tra độ sâu nút cây khi tạo hoặc kéo thả. Trả lỗi nếu vượt quá 5.
BR-MOD-02 Không được xóa Module nếu còn chứa Test Case hoặc Module con. Kiểm tra HasChildren / HasTestCases. Chặn xóa nếu còn dữ liệu.
BR-ATT-01 Chỉ chấp nhận file: hình ảnh, video MP4/WebM, PDF, CSV, text log, HAR. Kiểm tra Magic Byte và Content-Type khi upload. Chặn file thực thi (.exe, .bat).
BR-ATT-02 Giới hạn dung lượng mỗi file tối đa 10 MB. Kiểm tra kích thước trước khi stream lưu trữ. Trả HTTP 413 Payload Too Large.
BR-ATT-03 Mỗi TestExecution tối đa 20 file; mỗi TestCase tối đa 10 file. Đếm số lượng file hiện có trước khi cho phép tải thêm.

    public DbSet<TestRunItem> TestRunItems { get; set; }
    public DbSet<TestExecution> TestExecutions { get; set; }
    public DbSet<TestStepResult> TestStepResults { get; set; }
    public DbSet<DefectLink> DefectLinks { get; set; }
    public DbSet<Attachment> Attachments { get; set; }

Phụ Lục: Bảng Thuật Ngữ Nghiệp Vụ (Glossary)

Bảng đối chiếu 20 thuật ngữ kiểm thử doanh nghiệp và kiến trúc ABP Domain-Driven Design:

Thuật ngữ Tiếng Việt Định nghĩa chuẩn hóa
Test Case (TC) Kịch bản kiểm thử Tập hợp các bước thực hiện kèm dữ liệu test và kết quả mong đợi, dùng để kiểm tra 1 tính năng cụ thể.
Test Step Bước kiểm thử Một hành động đơn lẻ trong kịch bản, gồm Action, Test Data, Expected Result.
Test Suite / Module Nhóm kịch bản / Phân hệ Nút trong cây thư viện, dùng để nhóm các TC theo tính năng hoặc phân hệ phần mềm.
Test Plan Kế hoạch kiểm thử Kế hoạch tổng thể cho 1 Release hoặc Sprint, gắn Milestone, mô tả phạm vi.
Test Run Đợt chạy kiểm thử Một đợt thực thi cụ thể thuộc Test Plan, với Environment và danh sách TC cần chạy.
Test Run Item Hạng mục trong đợt test Một TC cụ thể nằm trong 1 Test Run, gắn với phiên bản (TestCaseVersion) và tester được phân công.
Test Execution Lần thực thi Một lần chạy cụ thể của một TestRunItem. Một item có thể có nhiều lần chạy (Attempt 1, 2, 3...).
TestCaseVersion Phiên bản kịch bản (Snapshot) Bản chụp bất biến (immutable) toàn bộ nội dung TC tại thời điểm được duyệt. Đảm bảo kết quả test không bị ảnh hưởng khi TC gốc thay đổi.
Milestone Mốc thời gian Sprint, Release hoặc giai đoạn dự án. Thuộc Project, gắn vào TestPlan (KHÔNG nằm trong cây thư viện TC).
Requirement Yêu cầu phần mềm User Story hoặc đặc tả yêu cầu, dùng để truy vết liên kết giữa yêu cầu và TC (RTM).
RTM Ma trận truy vết yêu cầu Requirement Traceability Matrix — Bảng ánh xạ Requirement ⟷ Test Case ⟷ Execution Result.
Quality Gate Cổng chất lượng Bộ ngưỡng tiêu chuẩn (Pass Rate ≥ 95%, 0 Blocker...) phải đạt trước khi đóng Test Run.
Sign-Off Report Biên bản nghiệm thu Tài liệu chính thức xác nhận kết quả kiểm thử, có chữ ký QA Lead và Product Owner.
Flaky Test Kịch bản bất ổn Test Case cho kết quả không nhất quán (lúc Pass lúc Fail) với cùng điều kiện kiểm thử.
Defect Link Liên kết lỗi Bản ghi liên kết giữa một lần chạy test (TestExecution) với bug trên Jira, GitHub, Redmine.
Severity Mức độ nghiêm trọng Thuộc tính đánh giá độ nguy hiểm của Bug/Defect (Blocker → Trivial). KHÔNG thuộc Test Case.
Priority Mức độ ưu tiên Thứ tự ưu tiên chạy test (P1 Critical → P4 Low). Thuộc Test Case.
Automation ID Mã ánh xạ tự động Chuỗi định danh (vd: Namespace.Class.Method) dùng để ánh xạ kết quả CI/CD với TC trong hệ thống.
ABP Module Module ABP Gói phần mềm độc lập theo chuẩn ABP Framework, có thể cắm (plug) vào bất kỳ ứng dụng ABP nào.
Reusable Module Module tái sử dụng Module được thiết kế bao đóng để dùng chung cho nhiều ứng dụng (Host App) mà không cần sửa mã nguồn.
